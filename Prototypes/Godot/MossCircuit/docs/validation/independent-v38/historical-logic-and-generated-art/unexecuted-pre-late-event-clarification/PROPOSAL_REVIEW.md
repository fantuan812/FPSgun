# v38 Stitch Drone proposal: independent static review

Status: direction suitable for a precise contract, NOT approval to implement or execute. Proposal SHA prefix7b060b29; baselinev37 remains unchanged. Reviewed proposal and actual baseline EnemyAI/CombatRuntime/weapon/effect HP seams only; no target tests.

## Strong constraints worth retaining
One finite support unit, no new player module or resistance rule. Source drone can be interrupted by any actual HP reduction; target injury alone is not an interrupt. No self/support/boss/parented-child healing, stable identity, immediate bounded HP repair with no resurrection, no RNG for target choice, and late settlement after all existing damage/procs. Existing damage rules stay untouched. Distinct silhouette/tether/plus communicates a tactical choice, not a color-only overlay.

## Contract blockers to resolve before oracle freeze
1. **Exact acquisition/position phase.** Current combat step fires weapons and advances mortars/hazards before sequential enemy AI/movement/clamp, then hostile/projectile contacts and player projectiles. Acquiring during that sequential loop can read earlier targets at new positions and later targets at old positions. Choose a precise shared acquisition phase/snapshot or explicitly preserve/test its order dependence; stable target-ID tiebreak alone does not solve mixed-time positions. Source HP snapshot timing must distinguish pre-entry early damage from same-step late damage. State whether a newly acquired drone has already moved this tick.
2. **Channel and cooldown state machine.** Define whether channel-entry tick consumes dt (recommend no retroactive full-dt deduction), exact <=0 deadline, one pulse maximum for large dt, and cooldown start/reset timing for success, source hit, lost target, full target, out-of-range and terminal cancellation. Is range checked each tick with immediate cancel, or only acquisition/completion? Can a target become full then wounded again during a channel? These are observably different rules. Failed acquisition1s retry and successful/cancelled5s must not accumulate catch-up credit. Pause does not advance either timer.
3. **Late dead-but-present actors.** Runtime's reverse death loop can kill an already visited actor through a later kill proc; pickup procs happen after death traversal. A dictionary may remain present with HP<=0 until the next step. Settlement must test currentHP>0 for both actors, not just membership or queued intent. Do not add a second old death/reward flush merely to support repair; that would change legacy event ordering. Recheck playing after all late phases and do not heal terminal/direct nonplaying steps.
4. **Every actual source HP-loss path.** Baseline weapon_combat has four primary write sites and effect_runtime has multiple hit/radial/arc/echo/hazard/mortar/feedback writes. Produce a static path-to-runtime-test matrix, not just generic positive-damage policy tests. A source-only HP snapshot is valid while all support actors are excluded from every new heal source and baseline has no enemy healing. Specify observable HP reduction rather than merely a damage command, and test zero damage, chill-only, pull-only (with separate range cancellation), source hit before entry, after entry and exactly due. Target injury should remain repairable if alive. No future-heal assumptions presented as permanent guarantees.
5. **Stable-ID multi-source semantics.** Normal encounter spawn cap1 does not remove the need to test two valid supplied sources. Sorted sourceID settlement must re-evaluate target HP after each heal, clamp to max and explicitly classify a now-full target as wasted/cancelled. Reject duplicate/invalid IDs in test-policy inputs or state the world-ID invariant. No retaining target Dictionary aliases across removals/reset.
6. **Bounded encounter/RNG change.** Rooms CROSSFIRE/BROOD append exactly one entry, preserve four originals and coordinates. Arena onlywave4 changes its pool and adds support cap1; later RNG state can still differ, so don't claim unchanged later whole-run sequences. Cap counts only living support and is applied only at the specified ordinary spawn seam. Old config with no support fields must preserve the original RNG calls and byte traces. Define fallback for a cap-filtered empty pool, malformed pool and unsupported configuration rather than accidentally indexing empty/RNG-modulo0. Keep old fixed encounter/pool controls separate from intentionally changed current encounters.
7. **Data types and finite bounds.** Freeze exact field names/schema, permitted numeric representations (JSON integral float where appropriate, bool rejected), finite positive range/channel/cooldown/heal and any caps. Missing optional new fields in old rows must remain valid, but a declared support row cannot silently become inert after malformed config. Do not alter historical generic rules without explicit scope.
8. **Animation/visual state consistency.** Current runtime sets enemy.anim_hp before death/pickup phases. A late heal can leave anim_hp below actual HP, potentially masking a smaller future hurt cue. Specify reconciliation without erasing an already-triggered hurt/death animation. Live tether eligibility must exclude dead-but-present sources/targets and retained death sprites. Cap completion/interruption effects per source and globally; clear across title/restart/room transitions. Progress must remain understandable with reduced flash and at960, plus marker distinct from existing medical pickups/player effects.
9. **Finite resource/native evidence.** New silhouette/channel/death assets and manifests must be real authored resources, not a fallback recolor passed off as final art. Exact PCK resource/image identity, controlled native source-target attribution, interruption, target death and successful pulse should be observed. Ordinary run reports only actual events reached; no seed reroll to force the new enemy. Full source suite and existing shop/audio/RunFlow regressions remain mandatory.

## Suggested freeze order
Exact contract/API/state machine + old-RNG compatibility plan -> independent handwritten target/range/timer/ordering oracles -> explicit implementation approval -> first cold/focused finite routes. Do not initialize expectations from target output. No production, target or new side gameplay was started for this review.
