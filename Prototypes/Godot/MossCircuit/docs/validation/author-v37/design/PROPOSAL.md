# v37 candidate: Shop Build Forecast (read-only proposal, not implemented)

## Player outcome
Before BUY or destructive weapon replacement, show a compact **AFTER PURCHASE** comparison: remaining scrap, weapon/module occupancy, mechanisms gained/lost/still missing, and real weapon readouts under the projected build. Choosing the replacement slot immediately updates this comparison. In particular, replacing the last Return Disc visibly disables Scavenger Return/Return Sustain; replacing one of two copies does not. Buying Fracture Coil with Cryo alone must say **still missing a different weapon type**, not promise an active combo. This makes existing 8 weapons/30 modules meaningfully easier to assemble, without another multiplier, new loot-pool entry, extra reward or RNG change.

## Concrete current code evidence
- `scripts/main.gd:997–1083` `_view()` builds current synergy status and current shop bias. The offer gets a base weapon readout, not a hypothetical post-transaction build. There is no per-offer before/after mechanism transition.
- `main.gd:1021–1034` already honors `requires_other_weapon_than`, including Cold Snap's third prerequisite. This semantic source should be shared rather than cloned with simpler pair logic.
- `main.gd:1044–1050` already uses a projected build for tempering preview: a useful local precedent, but currently only that action has projection.
- `ui/moss_ui.gd:244–270` item cards can show current prerequisites in ITEM DETAILS. Weapon cards do not show those item mechanism statuses. `:408–421` replacement selection changes only the purchase payload; it does not show which active mechanisms the chosen lost slot breaks.
- `main.gd:840–870` real `_buy` remains authority; `Rules.transaction` mutates the actual build only after controller guards. Existing replacement destruction/no refund and tier-reset behavior must remain unchanged.
- Enemy readability already has charger brace/front-angle tactics and data-driven tells/dodge text (`data/encounters.json`), so another generic enemy-warning overlay is not chosen without a separately demonstrated gap.

## Finite design boundary
1. Shop BUY and REPLACE only. No sell/temper/reservation-management forecast in this unit; no drag-and-drop, recommendation ranking, automatic purchase, new modal step or combat HUD.
2. Pure projection on detached build/catalog inputs. Reuse `Rules.transaction` on the detached build, followed by `Rules.derive` and existing WeaponReadout. Never invoke `_buy`, `_recompute`, effects sync, RunFlow or RNG for preview. Controller state/generation/sold/reserved validity must gate projection; a forecast is not authorization.
3. Resolve build mechanisms using existing catalog `requires` and optional `requires_other_weapon_than`, in catalog order. Extract one shared read-only status resolver if necessary; prove current status bytes unchanged. Optional absent mechanism IDs remain supported; do not key solely by display name or require new IDs on legacy rows.
4. Display explicit unavailable reason instead of a fake successful after-state for insufficient scrap/full module slots/stack cap/invalid tier metadata/stale or invalid reservation. A full weapon bag projects the selected existing slot, not an invented default sale. New purchases stay STANDARD; tempered replaced copies are destroyed, no refund.
5. Numerical scope is weapon primary readout and scrap/slot counts only. Do not present DPS, enemy damage, healing, cooldown reset, forecasted active projectiles, shield recharge, ordinary acquisition or guaranteed shop bias. Derived max HP is not free healing. Unchanged old weapons need not flood the compact card; changed/new/replaced slot rows can live in a disclosure.
6. Launch-snapshot caution remains explicit where relevant: purchase preview describes the next equipped build, not retrofitting old Return/Bankshot shots or ongoing dashes. Existing transaction-specific projectile clearing remains authority, not simulated by UI.
7. UI: persistent compact text-labelled state chips **ENABLES / DISABLES / STILL NEEDS** with existing partner icons; selected-slot label and old→new slot strip. Moss/amber plus distinct glyphs, never color-only. One small original code/vector connector/check/broken-link treatment; do not copy external assets. Data-driven existing item/mechanism text, no catalog expansion or new balance data. Keep actual action buttons and keyboard focus stable, 960×540 scroll-safe.

## Freeze before implementation
Specify exact projection output schema, guard precedence, shared-status compatibility, slot selection/focus refresh behavior, empty/malformed detached inputs, visibility and stable ordering. Validate no partial transaction mutation escapes. No hover-only essential information. Confirm projected state is detached even when consumer mutates nested arrays. Production work starts only after contract + independent oracle freeze in a new directory; v36 remains immutable.

## Independent oracle and finite acceptance scope
- Hand-derived transitions: Reel + Return gained/lost; duplicate Return replacement retains; Cryo+Fracture without third type remains inactive, replacement of last non-Cryo disables; unrelated purchase changes no mechanism; old optional-ID rows supported.
- Three existing tag thresholds: crossing up/down, matching weapon applicability, module copies vs weapon copies; no new threshold or fixed-module scaling.
- Transaction comparisons: on separate actual game instances, forecast equals real successful purchase/replacement resulting build/readout for selected slots including tempered donor destruction; insufficient coins/full items/stack cap/sold/stale generation/invalid held offer rejected. Existing six-transaction/24-combat old catalog traces must remain exact; unchanged catalog means existing current-shop traces should also remain exact.
- Purity: repeated previews and slot switches leave original nested build/catalog, RNG state, offers/generation, RunFlow, HP, cooldowns, hazards, bullets/audio untouched; mutate returned report cannot mutate inputs. Real purchase remains exactly once through existing authority.
- UI: native controlled shop at both minimum and normal size, actual replacement selector changes forecast, real click commits shown slot and generation, reserved offer and insufficient-scrap states, long missing-prerequisite wrapping/scroll/focus; original screenshots reviewed. Ordinary one-attempt observation separate, no claim every combo naturally acquired.
- Full discovered regression with original strict per-case budgets/errors. Actual packed feature/UI/resource checks, source parity and bounded cleanup; preserve any failures. No new audio, Windows/performance/all-build balance claims.

## Why this unit now
Recent units already added several bespoke interactions and a new original icon; the current shop still requires mentally combining a current-status panel, base offer readout and destructive replacement selector. A truthful immediate after-state supplies actionable build decisions with existing content, not a new audit document. Enemy behavior or another weapon remains a later independent content unit, not bundled here.
