# v37 Shop Build Forecast — C3 pre-implementation contract

Status: proposed exact contract for independent review and oracle freeze. No production implementation or target execution yet. Base is immutable v36 accepted-local source717, production131. This feature is a read-only aid to BUY / REPLACE, not a transaction authority or future combat prediction.

## A. Player-visible scope
Every unsold shop offer has a compact AFTER PURCHASE summary. Item and non-full-bag weapon purchases use append mode. A full weapon bag uses its existing replacement selector: initially the first displayed real slot (existing slot0, displayed as CURRENTLY SELECTED SLOT 1), then whichever real slot the player selects. Changing selection immediately changes only that card's forecast; no controller intent, game mutation, generation increment, reroll or full UI rebuild. Existing BUY/REPLACE controls remain the only commit action and retain original payload/authority.

Summary budget at minimum960×540: at most three wrapped text rows beneath the action/selection, excluding existing card description. Row1 remaining scrap + slot occupancy; row2 ENABLES/DISABLES counts and at most one name (loss takes display priority); row3 relevant STILL NEEDS count, or explicit no mechanism change. Full names, prerequisites, changed tag thresholds and weapon readout details are collapsed by default in one BUILD DETAILS disclosure. Text+distinct plus/minus/link glyph, not color-only. No essential failure reason or destructive-replacement warning hidden inside disclosure. Existing independently scrollable offer/bag columns retained. Do not duplicate entire current-build status panel inside every card.

Invalid purchase shows UNAVAILABLE plus the reason; no after-values, successful transition chip or fake damage values. Sold cards show SOLD / no forecast. A single brief always-visible label establishes "Equipped-build preview, not guaranteed damage"; readout details preserve existing primary-only/not-DPS notes. No new audio, new catalog rows, pool weights, balance changes, confirmation modal, automatic recommendation, sell/temper forecast or persistent preferences.

## B. Purity evidence and permitted call graph
Base `scripts/rules.gd:257–281` transaction only reads catalog_entry and WeaponTempering.metadata_error then writes the supplied build's coins, weapons, optional weapon_temper, items and revision. Every rejection precedes writes. It has no RNG, filesystem, resource loading, scene nodes, callbacks, signals, effects, RunFlow or globals. `derive:221–255` starts with a deep duplicate of base, reads build/catalog and computes stats. `WeaponReadout.describe` calls shared numeric Rules functions, no side effects. `Reservation.matches/invalid_reason` only read data; never call Reservation.draw/create.

Forecast must first deep-copy the supplied build. Execute Rules.transaction only on this detached copy. No references to RNG/session/effects/scene are accepted by the pure API. Never call `_buy`, `_recompute`, effects.sync, RunFlow, emit, rig operations or draw_shop. Catalog/base are readonly; returned arrays/dictionaries must also be detached. Real `_buy` and Rules.transaction are not modified by this unit. `_view` may call shared pure forecast/status functions only.

## C. Exact API and output
New `scripts/gameplay/build_forecast.gd`, static:
`project(base:Dictionary, build:Dictionary, catalog:Dictionary, id:String, replace_slot:Variant=-1)->Dictionary`.
Input contract: base/catalog are already application-validated, build is a live valid run build except deliberately invalid weapon_temper metadata covered below. This is not a new universal schema validator. Do not execute on unknown IDs or malformed slot types. Actual integer slot only, not bool, float or string. Allowed -1 (append), or 0..weapons.size()-1 for a weapon. Any other negative/out-of-range value rejects `Invalid replacement slot`. Items require -1; nonnegative rejects `Item purchases do not replace weapons`. These are preview input grammar checks, not changes to real transaction policy.

On failure return exactly `{available:false, reason:String}`. Unknown ID uses `Unknown item`; slot grammar checked after known entry, before transaction. Otherwise Rules.transaction's exact reason and precedence applies (metadata, affordability, stack, slots). On success return:
```
{available:true, reason:"", id:String, replace_slot:int,
 coins_before:int, coins_after:int,
 weapon_count_before:int, weapon_count_after:int,
 item_count_before:int, item_count_after:int,
 removed:Dictionary, added:Dictionary,
 mechanisms:Array, tags:Array, weapons:Array,
 weapon_readouts_available:bool, weapon_readout_warning:String}
```
Item counts mean distinct occupied module slots, not total copies. `removed` is {} except explicit weapon replacement, when `{slot:int,id:String,name:String,tier:int}` records destroyed copy; `added` is `{kind:String,id:String,name:String,slot:int,tier:int}`, with weapon resulting slot and STANDARD tier0; item slot=-1,tier=0. For item purchases with invalid weapon_temper metadata, the real transaction can still succeed: preserve available=true, mechanism/tag/coins/count report, but set weapon_readouts_available=false, weapon_readout_warning to the exact metadata_error and weapons=[]; never claim that purchase is rejected. For valid tier metadata set weapon_readouts_available=true and warning="". No fabricated STANDARD fallback numeric readout. Weapon purchases continue to reject the metadata error through real transaction policy. No actual build/stats object is exported. Report no HP change, healing, cooldown/reset, active projectile or shield promise.

`mechanisms` contains only (a) active-before != active-after or (b) still inactive after and offered ID is in that mechanism's explicit `requires`. Rows in catalog order:
`{index:int,before:Dictionary,after:Dictionary,change:String}`. before/after are full detached legacy mechanism-status records, with exactly the original name/active/requires/missing/description keys.
change exactly `enables`, `disables`, `needs` as appropriate. after.missing uses existing readable prerequisite names including "a weapon type other than Cryo Sprayer". A currently active unchanged relation is omitted. Do not show every unrelated inactive pair. A row whose optional `requires_other_weapon_than` is satisfied/removed by another weapon still appears for real activation/deactivation even when offer ID is not in requires. Use row index+catalog order, not display-name identity or mandatory ID; legacy rows without `id` remain valid. No new proc activation rules.

`tags` contains only existing tag-rule status changes in count OR active OR matching equipped weapon list. Each row `{index:int,before:Dictionary,after:Dictionary}` contains detached exact `Rules.tag_synergy_status` records in existing rule order. Counts from owned copies remain authoritative. Details must distinguish activating an existing threshold from a new extra effect; fixed proc damage stays unscaled.

`weapons` is per resulting slot in ascending order with `{slot:int,id:String,name:String,tier:int,before:Dictionary,after:Dictionary}`. `before` is existing same-slot equipped readout (or {} for append); `after` is shared WeaponReadout.describe(current=true) using projected derive and actual resulting tier. Replacing slot compares its destroyed copy to new STANDARD even if same weapon ID; others preserve copy tiers. All rows returned for testability; UI details may omit byte-equal before/after rows. Readout `scope:CURRENT` is internal existing numeric adapter semantics, not a current-world claim; UI heading must say PROJECTED EQUIPPED STATS. Do not call DPS or simulate target defenses.

## D. Controller/view guards and generation
Expose read-only `_offer_forecast(index:Variant,generation:Variant,replace_slot:Variant=-1)->Dictionary`. It returns the same failure shape before pure projection in this precedence: state!=shop, non-int generation or generation mismatch -> `Shop view expired`; then non-int/out-of-range index -> `Offer unavailable`; then sold -> `Offer already sold`; then weapon entry + invalid weapon_temper -> exact metadata_error; then matching reservation invalid -> `Reserved offer unavailable: ` + Reservation.invalid_reason; then pure project slot grammar and Rules.transaction. This follows real _buy state/generation/index/sold -> weapon-tier -> held-reason -> transaction ordering; all three strict integer checks (index, generation and replace_slot) are preview-only input grammar, not an authority change. Existing _on_intent("buy") coerces these payload values using int(...), and typed _buy arguments do not establish strict rejection at that intent boundary. This unit leaves those real intent coercions and transaction guards unchanged, does not claim actual purchases reject every non-int payload, and tests preview rejection separately from real transaction behavior. Otherwise pure project with real catalog price; held price is an identity constraint, not an override. Invalid weapon_temper does not reject an otherwise valid item transaction; its numeric weapon forecast is separately unavailable as above.

When `_view` builds an offer it adds `forecast_options:Array` to the detached view only: one `{replace_slot:-1,report:...}` for item or nonfull weapon bag; full weapon bag one per actual weapon slot in slot order. These are computed from the same generation as the view. UI reads these precomputed reports without receiving live build. No new controller action is added. Existing buy payload generation remains original and stale clicks still rejected. Full re-render after actual sale/buy/refresh/order/temper/reservation changes recomputes forecasts; no cached forecast survives those generation changes. Dropdown selection stays local until existing rebuild semantics occur; do not promise persistence across a rebuild.

## E. Shared mechanism status
Move only the existing `_view` mechanism status calculation into a pure `BuildForecast.mechanism_status(build,catalog)->Array` or a lower-level standalone pure helper if needed to avoid preload cycles. Returned legacy row shape must remain exactly `{name,active,requires,missing,description}`, including original order and ScavengerReel validated description. `_view.synergy_status` delegates to it with byte-equivalent results on all old valid catalogs and no-id rows. No catalog schema tightening. Avoid Rules -> BuildForecast -> Rules preload cycles; Rules itself need not depend on forecast.

## F. Important exact examples
- Reel+Return: buying either missing component enables; replacing the last Return with another type disables; replacing one of two Return copies retains active and produces no mechanism transition.
- Cryo+Fracture with no other weapon: buying Fracture produces NEEDS different weapon, not ENABLES. Adding Rivet enables even though Rivet is not explicit requires; replacing last other type with Cryo disables. Duplicate Cryo never supplies the other type.
- Buying a module already at cap or item slots full produces only unavailable, even when that module would otherwise complete a pair. Not enough scrap produces no hypothetical positive affordance. Buying a new weapon into full bag requires an actual selected slot. Replacing a tempered copy gives new tier0; remaining tempered copies keep theirs.
- Arc Grid / Saw Rig / Scatter Rig use current count and matching lists; can activate without a matching weapon, in which case existing qualifier says no equipped beneficiary. No fourth/fifth tag threshold. Fixed Fracture/Diode/procs stay separate from weapon scaling.
- Held offer remains not owned until real purchase; preview does not change its token/slot/offer/price, reserve or draw. Invalid held identity cannot be bypassed via projection.
